## О проекте

Open-world 3D-игра на Flutter/Dart в духе GTA, но с оригинальными ассетами.
Мир — реальный Южный район Оренбурга вокруг дома игрока (ул. Весенняя, 3,
51.715510, 55.107186). Разрабатывается как последовательность вертикальных
срезов, а не одним махом.

Репозиторий: https://github.com/nekiymolla/oren-crime-game-3d

## Ключевые технические решения (и почему)

- **flutter_scene** (не Unity/Godot-embed) — чтобы вся геймплейная логика
  была на Dart, как и просил пользователь, а не в GDScript/C# за
  PlatformView. Пакет на момент разработки перешёл на **stable**-канал
  Flutter (3.47+), хотя часть его собственной документации (и README
  саб-пакетов вроде flutter_scene_rapier) всё ещё пишет "требует
  master" — это устаревшие доки, ориентироваться нужно на реальный
  `flutter pub add`/resolve, а не на текст README.
- **FVM** — Flutter SDK этого проекта закреплён отдельно от других
  проектов пользователя на этой машине (`.fvmrc` = 3.47.4).
- **flutter_scene_rapier (Rapier-физика) — сознательно НЕ используется.**
  Оценивали для машины: пакет experimental, нет готового компонента
  "машина", только голые rigid body/joints — пришлось бы строить
  raycast-подвеску с нуля поверх экспериментального FFI-пакета. Вместо
  этого — собственный **kinematic**-контроллер
  (`lib/vehicles/vehicle_controller_component.dart`) с аркадным GTA-like
  ощущением (нелинейный разгон, руление по скорости, занос через grip
  falloff) и раздельно добавленными raycast-коллизиями (см. ниже). Не
  предлагать Rapier повторно как "быстрое решение" — уже разбирали.
- **OSM → osm2world → glTF** пайплайн в `tools/osm_pipeline/` (скрипты
  `setup_osm2world.sh`, `fetch_osm_data.sh`, `convert_to_glb.sh`). Сам
  `osm2world` (~470 МБ) и сырой `.osm` — НЕ в git (см. .gitignore),
  качаются заново при необходимости. В git — только готовый
  `assets/models/world/yuzhny_district.glb`.

## Что сделано

### Phase 1 — технический прототип
- Flutter-проект на flutter_scene 0.23.0, модульная структура `lib/`.
- 3D-сцена: террейн-плейсхолдер (плоскость), направленный свет + небо
  (`GradientSkySource` + `EnvironmentMap.fromSky` для ambient-света).
- Игрок: капсула-плейсхолдер, `ThirdPersonControllerComponent` (движение,
  прыжок, коллизии со сценой — встроены в компонент из коробки).
- Камера: `FollowCameraController` (orbit по drag), camera-relative
  движение игрока (`cameraHeadingYaw` в setMoveInput).
- Тач-джойстик + кнопки бег/прыжок, адаптивный под ориентацию HUD.
- Debug-оверлей FPS.
- Проверено на Android-эмуляторе, iOS-симуляторе и на реальном iPhone 13
  (важно: баг "чёрная половина экрана" на iOS-симуляторе оказался багом
  МОЕГО способа скриншотить через `xcrun simctl io screenshot`, а не
  движка — реальный рендер на симуляторе был в порядке).

### Phase 2 (начало) — реальная геометрия района
- OSM-пайплайн (см. выше) сгенерировал реальные дороги/здания квартала
  вокруг дома игрока, загружаются через `loadScene()` в `lib/world/district.dart`.
- Overpass-запрос пока берёт только `highway` и `building` — НЕТ
  `landuse`/`natural` (газоны, тротуары), поэтому между зданиями видна
  плейсхолдер-земля (плоскость чуть ниже нуля) как подложка.
- Дорожного графа для AI (NPC/трафик) пока нет — только визуальная
  геометрия, по ней можно только гулять/ездить, навигационных данных нет.

### Phase 3 (начало) — машина
- `VehicleControllerComponent` — kinematic-физика: газ/тормоз с
  нелинейным разгоном, руление по "велосипедной модели" (радиус поворота
  зависит от скорости), занос на высокой скорости (grip falloff — вектор
  скорости "отстаёт" от разворота носа).
- **Коллизии машины со зданиями** — raycast по трём точкам переднего
  бампера (`raycastNode` против сцены), машина останавливается перед
  препятствием. Не проверено юнит-тестом (CuboidGeometry требует живой
  GPU-контекст даже для конструирования — headless `flutter test` не
  может создавать геометрию), проверено только вживую в игре.
- Камера при вождении **сама доворачивается за курсом машины**
  (`Game.tick()` + `FollowCameraController.orbitBy`), если игрок не
  крутит вид сам (флаг `userIsAdjustingCamera`, ставится `Listener` в
  `GameHud` поверх зоны `CameraControls`).
- Процедурная модель: низкий кузов + кабина со сдвигом к корме (силуэт
  седана) + фары-эмиссивы + 4 колеса-цилиндра. Не настоящая 3D-модель.
- Посадка/высадка: кнопка (иконка машины) видна только когда есть смысл
  (`VehicleInteractButton` следит за дистанцией через свой `Ticker`, не
  дёргая весь HUD) — рядом с машиной пешком, или всегда за рулём (там это
  "выйти"). Радиус посадки — `Game.vehicleInteractRadius` (4 м).
- При вождении джойстик/бег/прыжок заменяются на выделенные кнопки
  газ/тормоз (справа) и руль-влево/вправо (слева) — `DrivingControls`.
- **Клавиатура** (WASD/стрелки, Shift, Space, E) работает и пешком, и за
  рулём через тот же `InputState`, что и тач-ввод — `KeyboardControls`,
  подключена в `GameHud`. Полезно для быстрого тестирования на
  Android-эмуляторе (эмулятор пробрасывает клавиатуру хоста).
- Пользователь протестировал руками: **машина реально останавливается
  перед домом** (коллизии работают), силуэт машины стал похож на седан.
  WASD сначала "дёргался" — исправлено (см. следующий пункт), но после
  фикса возникла **регрессия**, тоже уже исправленная (см. ниже).

### Регрессия клавиатуры — уже исправлена, но стоит перепроверить руками

Хронология одного вечера (17.09.2026), для контекста, если что-то ещё
всплывёт:

1. Пользователь: WASD дёргается ("рывками", то работает то нет).
2. Фикс №1: переписал `KeyboardControls` с event-based (onKeyEvent
   накапливает down/up) на **опрос `HardwareKeyboard.instance.
   logicalKeysPressed` каждый кадр через Ticker**. Причина дёрготни:
   на части платформ (похоже, и на проброс клавиатуры хоста в
   Android-эмулятор) автоповтор зажатой клавиши шлётся как быстрые пары
   KeyUp+KeyDown, а не честное "продолжает удерживаться" — это ломало
   накопленное по событиям состояние.
3. Пользователь: стало "очень медленно и одновременно не работает" —
   т.е. фикс №1 сломал ВСЁ управление (не только клавиатуру).
4. Диагностика: Ticker из фикса №1 писал `inputState.setMove(x,y)` и
   `inputState.isRunning` **каждый кадр безусловно**, даже когда ни одна
   клавиша не зажата (x=0,y=0). Это 60 раз в секунду затирало (0,0)/false
   поверх того, что только что установили джойстик/кнопки вождения сразу
   после нажатия — тач-ввод оказался забит клавиатурным "молчанием".
5. Фикс №2 (коммит a6323ad): клавиатура пишет в `InputState` только пока
   сама активна, плюс один кадр на отпускание (чтобы корректно
   остановить движение, начатое ею) — остальное время `InputState` не
   трогает вообще, тач-источники снова главные, когда клавиатура молчит.
6. Проверка: в этой сессии закончился лимит на просмотр картинок (см.
   ниже), пришлось проверять программно — pixel-diff двух скриншотов
   через PIL/Python (`ImageChops.difference` + гистограмма). Результат:
   **0% изменившихся пикселей в состоянии покоя (2 скриншота с интервалом
   в 1 сек, без ввода) против 24% после 2-секундного удержания кнопки
   газа** — машина точно поехала. Это достаточно уверенное подтверждение,
   но **пользователь ещё не проверил фикс №2 своими руками** — стоит
   попросить его перепроверить WASD и кнопки вождения в начале следующей
   сессии, на всякий случай.

**Урок:** когда несколько источников ввода (джойстик, кнопки, клавиатура)
пишут в один и тот же `InputState`, ни один источник не должен писать
"ничего не происходит" безусловно каждый кадр — только когда он сам
активен, плюс один кадр на явное отпускание. Иначе молчаливый источник
забивает активный.

## Ограничение сессии (17.09.2026 вечер)

В этом чате закончился лимит на просмотр скриншотов (слишком много
больших картинок за долгую сессию) — Read на .png стал возвращать "media
removed — rejected by API" даже после уменьшения разрешения. Похоже,
лимит завязан на историю конкретного чата, а не на время — новый чат
должен снять ограничение. Если это снова всплывёт: pixel-diff через
Python/PIL (`ImageChops.difference`, см. пример выше в истории коммитов/
разговора) — рабочий обходной путь для проверки "что-то изменилось между
двумя скриншотами", не требует смотреть картинку глазами.

## Важный урок по тестированию

Синтетические ADB-жесты (`adb shell input swipe`) ненадёжны для проверки
непрерывного/удерживаемого ввода (газ, руление) — свайп может завершиться
(и обнулить ввод через `onPanEnd`) раньше, чем успевает сработать
скриншот, давая ложное "не работает". Для физики/движения — писать прямой
`flutter_test` на компонент (`Node()` без меша не требует GPU, можно
конструировать headless и звать `fixedUpdate()` в цикле). Для геометрии/
столкновений юнит-тест не годится (создание `Mesh`/`Geometry` требует
живого Impeller-контекста) — там нужна ручная проверка в приложении.

## Известные ограничения / плейсхолдеры (осознанные, не баги)

- Все 3D-модели процедурные (капсула, коробки) — лицензионных ассетов нет.
- Нет `landuse`/`natural` в OSM-запросе — газоны/тротуары не сгенерированы.
- Нет дорожного графа для NPC/трафика/полиции.
- Нет NPC, полиции, оружия, экономики, сохранений, дня/ночи, погоды —
  ничего из этого ещё не начато.
- Машина одна, без вариантов, без урона/деформации кузова (см. решение
  про Rapier выше — деформация ждёт настоящей rigid-body физики).
