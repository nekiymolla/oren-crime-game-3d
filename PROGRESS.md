## О проекте

Open-world 3D-игра на Flutter/Dart в духе GTA, но с оригинальными ассетами.
Мир — реальный Южный район Оренбурга вокруг дома игрока (ул. Весенняя, 3,
51.715510, 55.107186). Разрабатывается как последовательность вертикальных
срезов, а не одним махом.

Репозиторий: https://github.com/nekiymolla/oren-crime-game-3d

## Ключевые технические решения (и почему)

- **flutter_scene** (не Unity/Godot-embed) — чтобы вся геймплейная логика
  была на Dart, как и просил пользователь, а не в GDScript/C# за
  PlatformView. Пакет на момент разработки перешёл на **stable**-канал
  Flutter (3.47+), хотя часть его собственной документации (и README
  саб-пакетов вроде flutter_scene_rapier) всё ещё пишет "требует
  master" — это устаревшие доки, ориентироваться нужно на реальный
  `flutter pub add`/resolve, а не на текст README.
- **FVM** — Flutter SDK этого проекта закреплён отдельно от других
  проектов пользователя на этой машине (`.fvmrc` = 3.47.4).
- **flutter_scene_rapier (Rapier-физика) — сознательно НЕ используется.**
  Оценивали для машины: пакет experimental, нет готового компонента
  "машина", только голые rigid body/joints — пришлось бы строить
  raycast-подвеску с нуля поверх экспериментального FFI-пакета. Вместо
  этого — собственный **kinematic**-контроллер
  (`lib/vehicles/vehicle_controller_component.dart`) с аркадным GTA-like
  ощущением (нелинейный разгон, руление по скорости, занос через grip
  falloff) и раздельно добавленными raycast-коллизиями (см. ниже). Не
  предлагать Rapier повторно как "быстрое решение" — уже разбирали.
- **OSM → osm2world → glTF** пайплайн в `tools/osm_pipeline/` (скрипты
  `setup_osm2world.sh`, `fetch_osm_data.sh`, `convert_to_glb.sh`). Сам
  `osm2world` (~470 МБ) и сырой `.osm` — НЕ в git (см. .gitignore),
  качаются заново при необходимости. В git — только готовый
  `assets/models/world/yuzhny_district.glb`.

## Что сделано

### Phase 1 — технический прототип
- Flutter-проект на flutter_scene 0.23.0, модульная структура `lib/`.
- 3D-сцена: террейн-плейсхолдер (плоскость), направленный свет + небо
  (`GradientSkySource` + `EnvironmentMap.fromSky` для ambient-света).
- Игрок: капсула-плейсхолдер, `ThirdPersonControllerComponent` (движение,
  прыжок, коллизии со сценой — встроены в компонент из коробки).
- Камера: `FollowCameraController` (orbit по drag), camera-relative
  движение игрока (`cameraHeadingYaw` в setMoveInput).
- Тач-джойстик + кнопки бег/прыжок, адаптивный под ориентацию HUD.
- Debug-оверлей FPS.
- Проверено на Android-эмуляторе, iOS-симуляторе и на реальном iPhone 13
  (важно: баг "чёрная половина экрана" на iOS-симуляторе оказался багом
  МОЕГО способа скриншотить через `xcrun simctl io screenshot`, а не
  движка — реальный рендер на симуляторе был в порядке).

### Phase 2 (начало) — реальная геометрия района
- OSM-пайплайн (см. выше) сгенерировал реальные дороги/здания квартала
  вокруг дома игрока, загружаются через `loadScene()` в `lib/world/district.dart`.
- Overpass-запрос пока берёт только `highway` и `building` — НЕТ
  `landuse`/`natural` (газоны, тротуары), поэтому между зданиями видна
  плейсхолдер-земля (плоскость чуть ниже нуля) как подложка.
- Дорожного графа для AI (NPC/трафик) пока нет — только визуальная
  геометрия, по ней можно только гулять/ездить, навигационных данных нет.

### Phase 3 (начало) — машина
- `VehicleControllerComponent` — kinematic-физика: газ/тормоз с
  нелинейным разгоном, руление по "велосипедной модели" (радиус поворота
  зависит от скорости), занос на высокой скорости (grip falloff — вектор
  скорости "отстаёт" от разворота носа).
- **Коллизии машины со зданиями** — raycast по трём точкам переднего
  бампера (`raycastNode` против сцены), машина останавливается перед
  препятствием. Не проверено юнит-тестом (CuboidGeometry требует живой
  GPU-контекст даже для конструирования — headless `flutter test` не
  может создавать геометрию), проверено только вживую в игре.
- Камера при вождении **сама доворачивается за курсом машины**
  (`Game.tick()` + `FollowCameraController.orbitBy`), если игрок не
  крутит вид сам (флаг `userIsAdjustingCamera`, ставится `Listener` в
  `GameHud` поверх зоны `CameraControls`).
- Процедурная модель: низкий кузов + кабина со сдвигом к корме (силуэт
  седана) + фары-эмиссивы + 4 колеса-цилиндра. Не настоящая 3D-модель.
- Посадка/высадка: кнопка (иконка машины) видна только когда есть смысл
  (`VehicleInteractButton` следит за дистанцией через свой `Ticker`, не
  дёргая весь HUD) — рядом с машиной пешком, или всегда за рулём (там это
  "выйти"). Радиус посадки — `Game.vehicleInteractRadius` (4 м).
- При вождении джойстик/бег/прыжок заменяются на выделенные кнопки
  газ/тормоз (справа) и руль-влево/вправо (слева) — `DrivingControls`.
- **Клавиатура** (WASD/стрелки, Shift, Space, E) работает и пешком, и за
  рулём через тот же `InputState`, что и тач-ввод — `KeyboardControls`,
  подключена в `GameHud`. Полезно для быстрого тестирования на
  Android-эмуляторе (эмулятор пробрасывает клавиатуру хоста).
- Пользователь протестировал руками: **машина реально останавливается
  перед домом** (коллизии работают), силуэт машины стал похож на седан.
  WASD сначала "дёргался" — исправлено (см. следующий пункт), но после
  фикса возникла **регрессия**, тоже уже исправленная (см. ниже).

### Регрессия клавиатуры — уже исправлена, но стоит перепроверить руками

Хронология одного вечера (17.09.2026), для контекста, если что-то ещё
всплывёт:

1. Пользователь: WASD дёргается ("рывками", то работает то нет).
2. Фикс №1: переписал `KeyboardControls` с event-based (onKeyEvent
   накапливает down/up) на **опрос `HardwareKeyboard.instance.
   logicalKeysPressed` каждый кадр через Ticker**. Причина дёрготни:
   на части платформ (похоже, и на проброс клавиатуры хоста в
   Android-эмулятор) автоповтор зажатой клавиши шлётся как быстрые пары
   KeyUp+KeyDown, а не честное "продолжает удерживаться" — это ломало
   накопленное по событиям состояние.
3. Пользователь: стало "очень медленно и одновременно не работает" —
   т.е. фикс №1 сломал ВСЁ управление (не только клавиатуру).
4. Диагностика: Ticker из фикса №1 писал `inputState.setMove(x,y)` и
   `inputState.isRunning` **каждый кадр безусловно**, даже когда ни одна
   клавиша не зажата (x=0,y=0). Это 60 раз в секунду затирало (0,0)/false
   поверх того, что только что установили джойстик/кнопки вождения сразу
   после нажатия — тач-ввод оказался забит клавиатурным "молчанием".
5. Фикс №2 (коммит a6323ad): клавиатура пишет в `InputState` только пока
   сама активна, плюс один кадр на отпускание (чтобы корректно
   остановить движение, начатое ею) — остальное время `InputState` не
   трогает вообще, тач-источники снова главные, когда клавиатура молчит.
6. Проверка: в этой сессии закончился лимит на просмотр картинок (см.
   ниже), пришлось проверять программно — pixel-diff двух скриншотов
   через PIL/Python (`ImageChops.difference` + гистограмма). Результат:
   **0% изменившихся пикселей в состоянии покоя (2 скриншота с интервалом
   в 1 сек, без ввода) против 24% после 2-секундного удержания кнопки
   газа** — машина точно поехала. Это достаточно уверенное подтверждение,
   но **пользователь ещё не проверил фикс №2 своими руками** — стоит
   попросить его перепроверить WASD и кнопки вождения в начале следующей
   сессии, на всякий случай.

**Урок:** когда несколько источников ввода (джойстик, кнопки, клавиатура)
пишут в один и тот же `InputState`, ни один источник не должен писать
"ничего не происходит" безусловно каждый кадр — только когда он сам
активен, плюс один кадр на явное отпускание. Иначе молчаливый источник
забивает активный.

## Ограничение сессии (17.09.2026 вечер)

В этом чате закончился лимит на просмотр скриншотов (слишком много
больших картинок за долгую сессию) — Read на .png стал возвращать "media
removed — rejected by API" даже после уменьшения разрешения. Похоже,
лимит завязан на историю конкретного чата, а не на время — новый чат
должен снять ограничение. Если это снова всплывёт: pixel-diff через
Python/PIL (`ImageChops.difference`, см. пример выше в истории коммитов/
разговора) — рабочий обходной путь для проверки "что-то изменилось между
двумя скриншотами", не требует смотреть картинку глазами.

## Важный урок по тестированию

Синтетические ADB-жесты (`adb shell input swipe`) ненадёжны для проверки
непрерывного/удерживаемого ввода (газ, руление) — свайп может завершиться
(и обнулить ввод через `onPanEnd`) раньше, чем успевает сработать
скриншот, давая ложное "не работает". Для физики/движения — писать прямой
`flutter_test` на компонент (`Node()` без меша не требует GPU, можно
конструировать headless и звать `fixedUpdate()` в цикле). Для геометрии/
столкновений юнит-тест не годится (создание `Mesh`/`Geometry` требует
живого Impeller-контекста) — там нужна ручная проверка в приложении.

## Диагностика лагов на слабом Android (RMX5303) — 17.09.2026

При первом запуске на реальном бюджетном Android (Realme RMX5303,
Unisoc ums9230 + Mali-G57, Impeller/Vulkan) FPS-оверлей показывал 2-15 FPS
и там же в чате пользователь подтвердил, что реально тормозит (не
артефакт скриншота). Разобрано по шагам, чтобы не наступать на те же
грабли повторно:

1. **Слияние мешей района ухудшило, а не улучшило** — `.glb` квартала
   содержал 1535 отдельных мешей на 9 материалов при всего ~10k
   треугольников (осознанный экспорт osm2world: меш на здание/сегмент).
   Слияние через `gltf-transform join` (1535 → 9 draw call'ов, тот же
   геометрический объём) на первый взгляд логичный фикс, но **сделало
   FPS хуже** (15 → 5, warmed): `flutter_scene`'s `raycastNode` (см.
   `raycast.dart`, используется built-in `ThirdPersonControllerComponent`
   и `VehicleControllerComponent` для коллизий) делает per-node bounding-
   box ранний отсев ПЕРЕД дорогим перебором треугольников — пока меши
   были маленькими (одно здание), почти все рейкасты отсеивались мгновенно;
   после слияния bounding box каждого из 9 мешей стал = весь
   загруженный регион, и КАЖДЫЙ рейкаст стал перебирать тысячи
   треугольников. **Урок: не мержить меши, по которым потом ходят
   raycastNode-коллизии, не проверив, что стало с их bounding box.**
   Слияние отменено, оригинальные меши по зданиям вернули.
2. **`renderScale` — самый честный сигнал fill-rate/GPU-стоимости.**
   `Scene.renderScale = 0.5` подняло FPS стоя с ~5-9 до ~30 (весь район,
   тени выключены) — подтверждает, что немалая часть стоимости это
   заливка пикселей (PBR-материалы + environment map по текстурам
   зданий), а не CPU. При ходьбе всё равно падало до ~12 — второй
   фактор ниже.
3. **9 рейкастов на кадр при ходьбе** — встроенный в пакет
   `ThirdPersonControllerComponent` (см.
   `~/.pub-cache/hosted/pub.dev/flutter_scene-*/lib/src/kit/character/
   third_person_controller.dart`) считает obstacle-avoidance ТОЛЬКО пока
   есть реальное движение (`horizMove.length2 > 1e-6`): 3 высоты x 3
   боковых смещения = 9 `raycastNode` в дополнение к 1 для земли. У
   машины похожий пробник бампера — но всего 3 луча, отсюда её меньшая
   просадка по сравнению с ходьбой. Каждый вызов `raycastNode` обходит
   ВСЕ узлы дерева сцены (даже там, где bounding box сразу отбрасывает
   меш) — то есть стоимость растёт с общим числом узлов в сцене, а не
   только с видимой геометрией.
4. **Физика без Rapier (`BasicSimulation`, чистый Dart-бэкенд из
   `package:flutter_scene/physics.dart`) — тупик для этой задачи.**
   Проверяли как альтернативу raycastNode-коллизиям: выяснилось, что
   `KinematicCharacterController` **не работает вообще** на
   `BasicSimulation` (`supportsCharacters == false`, `move()` кидает
   `StateError` — character-движение есть только у Rapier-бэкенда), а
   `TriMeshShape`-рейкасты у `BasicSimulation` деградируют до AABB всего
   меша, не до реальных треугольников (`shape_queries.dart`,
   `_rayAabb` для `TriMeshShape`/`ConvexHullShape`/`HeightFieldShape`).
   Не предлагать этот путь повторно без Rapier — уже разбирали, и Rapier
   для машины уже отдельно отклонён раньше (см. выше в файле).
5. **Реальный масштаб района — ~1900x1600 метров**, а не 200x200
   (плейсхолдер-земля `groundSizeMeters=200` вводила в заблуждение, это
   размер только самой земли-подложки). Из-за этого сделали
   пространственное чанкование: `tools/osm_pipeline/grid_split.mjs`
   (Node.js + `gltf-transform`, `npm install` в `tools/osm_pipeline/`
   один раз) режет сырой `.glb` на ячейки по `chunkSizeMeters`
   (`assets/data/world.json`), `lib/world/district_streamer.dart` держит
   в сцене только ячейки в радиусе `streamingRadiusChunks` от игрока/
   машины (обновляется в `Game.tick()`).
6. **Чанкование само по себе почти не подняло FPS на RMX5303** —
   похоже, `frustumCulled` (default true) и per-node bounding box и так
   уже дёшево отбрасывали далёкую невидимую геометрию ДО чанкования;
   чанкование убирает то, что и так не стоило дорого, а не ближние
   здания, чей fill-rate/тени и есть основная стоимость (см. пункт 2).
   `streamingRadiusChunks` уменьшили с 2 до 1 (91% → 44% геометрии в
   радиусе) — тоже не дало эффекта на этом устройстве, что подтверждает
   вывод. **Инфраструктура чанкования всё равно остаётся полезной** —
   пригодится, когда/если район расширят на весь Южный район целиком
   (сейчас загружены все ~46 ячеек сразу как ассеты, стриминг только
   решает какие из них добавлены в сцену).
7. **Итог: устройство — реальный узкий фактор**, не архитектура игры.
   Тот же билд на iPhone 13 (кабель) — стабильные 60 FPS без единой
   лишней правки. Решили тестировать вживую в первую очередь на iPhone
   13, Android RMX5303-специфичную оптимизацию (скорее всего дальше —
   `renderScale` + `shadowStatic` на статичных зданиях, раз рейкасты и
   чанкование не были узким местом) отложили на потом, не блокирует
   разработку фич.

## Пайплайн OSM: реальные баги, найденные и исправленные — 17.09.2026

Продолжение сессии выше (уже на iPhone 13). Пользователь попросил
расширить OSM-запрос на `landuse`/`natural`, чтобы убрать плейсхолдер-
землю в пустых местах — по пути всплыли три независимых реальных бага,
не связанных с самой задачей:

1. **Огромные "зонирующие" way утаскивают систему координат.** Overpass
   возвращает way ЦЕЛИКОМ, если хоть один его узел попал в bbox — один
   `landuse=residential` (административная зона на весь город, не
   визуальный газон) зацепил bbox краем и утащил узлы за километры.
   osm2world выбирает свой локальный (0,0,0) по общему bounding box'у
   всех узлов файла — один такой way сдвигал происхождение координат на
   сотни метров от geoOrigin. Фикс: `filter_oversized_ways.py`
   (вызывается из `fetch_osm_data.sh`) убирает way, чей lat/lon-размах
   больше bbox запроса в 3+ раза, — реальные крупные объекты (парк, пруд)
   проходят, зонирование на весь город — нет.
2. **osm2world молча выбирает свой (0,0,0), не наш geoOrigin.** Даже без
   огромных way обычная асимметрия соседних улиц/полигонов сдвигает
   происхождение на десятки-сотни метров. Фикс: `add_anchor_node.py`
   добавляет в сырой `.osm` перед конвертацией искусственное "здание"
   ровно в geoOrigin с уникальной высотой (`height=12345`, физически
   невозможное значение), `recenter.mjs` после конвертации ищет вершину с
   такой высотой, вычисляет её локальные координаты, сдвигает всю
   геометрию так, чтобы geoOrigin оказался в (0,0), и удаляет
   маячок-здание. Не зависит от того, как именно osm2world выбирает
   origin внутри себя — работает эмпирически для любой версии/конфига.
3. **osm2world без `--config` тихо теряет все текстуры.** Официальный
   `osm2world.sh` перед запуском делает `cd` в свою папку — только так
   находится `standard.properties` (материалы/текстуры) рядом с jar.
   Наш `convert_to_glb.sh` звал `java -jar OSM2World.jar` без этого,
   поэтому osm2world молча падал на голый fallback-стиль: 0 текстур,
   случайные материалы вроде `GARAGE_DOOR`/`MARBLE` почти чёрного цвета
   (не ошибка, не exception — просто выглядит криво). Фикс: явный
   `--config "$SCRIPT_DIR/osm2world_bin/standard.properties"` в
   `convert_to_glb.sh` — не зависит от cwd вызывающего, не нужен `cd`.
   **Если когда-нибудь здания снова станут беспричинно тёмными/без
   текстур — проверять это в первую очередь.**

Также по ходу дела:
- **Игрок спавнился внутри дома.** Адресная точка (geoOrigin) геокодируется
  в геометрический центр здания, а не во двор перед ним — раньше "везло"
  из-за бага №2 (спавн на 500 м в стороне, случайно на пустом месте).
  После починки координат стало видно по-настоящему. `WorldConfig.
  playerSpawn` (assets/data/world.json) — раньше объявлен, но НИГДЕ не
  читался в коде (игрок всегда спавнился в литеральном (0,0,0)); теперь
  подключён по-настоящему в `Game.load()`. Спавн игрока и машины перенесён
  в открытый парк рядом (`playerSpawn.positionLocal`), подальше от дома.
- **Debug-оверлей координат.** `GameView` теперь пишет x/z отслеживаемого
  узла (игрок/машина) в `DebugOverlayController` каждый кадр — можно
  сообщить точное место просадки FPS текстом, а не скриншотом.
- **Процедурная растительность.** Реальных отдельных деревьев
  (`natural=tree`) в OSM для этого района — 0 штук на весь квартал (не
  размечено, а не баг запроса — раньше их вообще не запрашивали, natural=
  tree это отдельный `<node>`, а не `way`, значит нужен свой `node[...]`
  Overpass-запрос). Вместо ожидания разметки — свои деревья:
  `lib/world/vegetation.dart`, `VegetationBatch` (два `InstancedMesh` на
  всю игру — стволы и кроны, один draw call на каждый вне зависимости от
  числа деревьев). `DistrictStreamer` при загрузке чанка кидает
  вертикальные `raycastNode` по случайным точкам внутри его квадрата — где
  ничего не находит (пусто, только плейсхолдер-земля), там сажает дерево;
  гарантированно не в зданиях/дорогах без отдельного анализа footprint'ов.

## Дорожный граф — 17.09.2026 (пока пользователь обедал)

`tools/osm_pipeline/build_road_graph.py` строит граф из `way["highway"]`
сырого `.osm`: узлы — точки изгиба/перекрёстки с координатами, рёбра —
последовательные пары узлов каждой дороги (с тегами `highway`/`oneway`).
Результат — `assets/data/road_graph.json` (уже в общем `assets/data/` в
pubspec.yaml, отдельной записи не нужно), в игре — `lib/world/road_graph.dart`
(`RoadGraph`/`loadRoadGraph()`).

**Калибровка координат расширена с одного маячка до трёх** (origin +
200м на север + 200м на восток, все — в `add_anchor_node.py`), чтобы
спроецировать lat/lon дорожного графа в ТУ ЖЕ систему координат, что и
геометрия района, не зная формулу проекции osm2world изнутри —
`recenter.mjs` теперь пишет `calibration.json` (эмпирические единичные
векторы "метр на север"/"метр на восток" в локальных координатах).
~~Важная находка при калибровке: +Z в этом движке указывает на юг~~ —
**неверно, исправлено 15.10.2026**: это было верно для координат glTF, а
движок при загрузке .glb переворачивает Z. В координатах игры север —
+Z; весь пайплайн теперь пишет данные в координатах игры (см. раздел
"Данные мира были зеркальны" и BUGS.md).

Пока у графа нет потребителя (NPC/трафик ещё не начаты) — только
отладочная визуализация: `buildRoadGraphDebugNode()` рисует тонкие жёлтые
линии вдоль дорог (`LineSegmentsGeometry` + `UnlitMaterial`), подключена в
`Game.load()`. Проверено на iOS-симуляторе (устройства пользователя были
недоступны в моменте): линия точно совпадает с настоящей дорогой в кадре,
спавн на нужных координатах, FPS 60. **Растительность и здания на том же
скриншоте не проверены глазами на предмет текстур/деревьев** — при
следующем живом тесте стоит явно посмотреть.

## Известные ограничения / плейсхолдеры (осознанные, не баги)

- Все 3D-модели процедурные (капсула, коробки, деревья-примитивы) —
  лицензионных ассетов нет.
- OSM-разметка реального района местами скудная (0 отдельных деревьев,
  всего 6 landuse/natural/leisure объектов на весь квартал) — открытые
  места заполняются либо плейсхолдер-травой (terrain.dart), либо
  процедурной растительностью (vegetation.dart), а не честной OSM-геометрией.
- NPC-пешеходы есть (простая state machine по дорожному графу, см. ниже),
  трафик/полиция по графу пока не ходят.
- Нет полиции, оружия, экономики, сохранений, дня/ночи, погоды — ничего
  из этого ещё не начато.
- Машина одна, без вариантов, без урона/деформации кузова (см. решение
  про Rapier выше — деформация ждёт настоящей rigid-body физики).

## NPC-пешеходы — 17.09.2026

`lib/pedestrians/pedestrian.dart` — чистая (без Flutter) логика: идёт по
прямой к текущей целевой точке дорожного графа, на прибытии выбирает
случайного соседа (не туда, откуда пришёл, если есть выбор), протестирована
юнит-тестами (`test/pedestrians/pedestrian_test.dart`) без GPU.
`lib/pedestrians/pedestrian_system.dart` — рендер и жизненный цикл: один
`InstancedMesh`-капсула на всех пешеходов сразу (один draw call вне
зависимости от количества), фиксированная популяция (16), спавн/деспавн
телепортацией рядом с игроком вместо создания-удаления узлов. **Намеренно
не использует built-in `ThirdPersonControllerComponent`** — у узлов графа
уже есть верная высота, доп. ground-рейкасты на каждого NPC были бы ровно
той же проблемой, что разбирали для игрока/машины утром (см. диагностику
лагов выше).

Проверено на iPhone 13 — пешеходы появились и ходят, но **FPS всё равно
заметно проседает и деградирует со временем даже после фиксов**
(жёсткий кап на число деревьев в `vegetation.dart` — растительность
раньше росла без ограничений весь сеанс; `shadowStatic` на узлах чанков
района — геометрия не меняется, пока чанк смонтирован, безопасный кейс
для кеширования тени). Оптимизация пешеходов/сцены в целом **сознательно
отложена** пользователем — см. пункт ниже.

**Баг найден пользователем**: пешеходы проходили сквозь здания — прямая
между двумя узлами графа иногда режет угол дома, а движение вообще не
проверяло препятствия. Фикс — не рейкаст каждый кадр (снова та же ловушка
с лагами), а рейкаст **один раз на ребро графа**, с кэшем по обеим
сторонам (`PedestrianSystem._isEdgePassable`/`_edgePassable`) — суммарная
стоимость ограничена числом рёбер во всём графе (≤805), а не числом
пешеходов или кадров. При выборе новой цели (на старте и по прибытии)
перекрытые рёбра пропускаются в пользу проходимых соседей. **Ещё не
проверено на устройстве** — сделано, пока телефон был не под рукой.

**Проверено на симуляторе 18.09.2026 — не помогло**, пользователь
подтвердил, что пешеходы всё равно проходят сквозь дома. Заодно
исправили кэш (раньше кэшировалось и "проходимо" — ложно, если чанк
здания ещё не успел асинхронно догрузиться к моменту первой проверки;
теперь кэшируется только подтверждённая блокировка, "проходимо"
перепроверяется каждый раз) и отфильтровали дорожный граф под пешеходные
типы `highway` (`pedestrianHighwayTypes` в `pedestrian.dart` — убрали
`tertiary`/`cycleway`, раньше пешеходы гуляли прямо по проезжей части
для машин). Второй фикс тоже не решил прохождение сквозь стены — баг
**отложен пользователем**, подробности и гипотезы, что проверить дальше
— в BUGS.md.

## Розыск (wanted) — ядро без погони — 17.09.2026

`lib/police/wanted_state.dart` (`WantedState`, 0-5 звёзд, глобальный
расшаренный стейт — как `GameModeState`) + `wanted_system.dart`
(`WantedSystem` — чистая логика, протестирована юнит-тестами без GPU):
наезд на пешехода (см. `PedestrianSystem.update()` — теперь принимает
позицию/скорость машины, при скорости выше 3 м/с и попадании в радиус
удара телепортирует пешехода и возвращает число наездов за кадр)
поднимает звёзды на это число; превышение скорости (>22 м/с, ~80 км/ч)
поднимает только до 1 звезды сразу, само по себе выше не растёт; без
новых нарушений 10 секунд — снимается по одной звезде. HUD —
`WantedStars` (справа сверху, опрос через свой Ticker, как
`VehicleInteractButton`), не виден при 0 звёзд.

**Сознательно не сделано в этом же заходе**: полицейских NPC/машин и
погони нет вообще — розыск растёт и падает сам по себе, ничего не
реагирует на игрока физически. Это отдельная, заметно более крупная
задача (спавн полицейских машин, pathfinding-преследование по дорожному
графу, условия ареста) — см. пункт 1 ниже.

## Тюнинг вождения + визуальные повреждения — 18.09.2026

По просьбе пользователя ("тормозит супер долго") — числа в
`buildPlaceholderSedan()` (lib/vehicles/vehicle.dart) и синхронно в
`assets/data/vehicles.json` (car_sedan_01, хоть он и не грузится кодом
напрямую — см. ниже): `acceleration` 8.2→16.0, `braking` 10.5→32.0,
`maxSpeed` 45.8 (165 км/ч)→55.6 м/с (200 км/ч).

Визуальные повреждения кузова — следующий пункт плана, сделаны сразу за
тюнингом. `lib/vehicles/vehicle_damage.dart` — чистая логика
(`VehicleDamageState`, `DamageLevel` pristine/damaged/wrecked), копит
скорость машины в момент каждого столкновения (`VehicleControllerComponent.
onCollision` — новый колбэк, зовётся ровно в момент остановки о
препятствие, до обнуления `velocityXZ`, т.е. несёт именно скорость
удара), удары слабее `minImpactSpeed` (2.5 м/с) не считаются. По
достижении порога (`damagedThreshold`/`wreckedThreshold`) переключается
видимость между тремя заранее построенными preset-узлами кузова
(`vehicle.dart`, `_buildBodyVariant`) — темнее краска, разбитые фары
(одна у damaged, обе у wrecked), тёмный "смятый" кубик на переднем
бампере крупнее у wrecked, у wrecked ещё и лобовое стекло светлее/матовее
(имитация трещин). Логика повреждений протестирована юнит-тестами
(`test/vehicles/vehicle_damage_test.dart`); сам факт переключения
видимости при реальном столкновении **не проверен на устройстве** —
нужно самому врезаться в стену и посмотреть.

**Побочная находка**: `assets/data/vehicles.json` на самом деле никогда
не читается кодом (как и было раньше с `world.json`'s playerSpawn, пока
не подключили) — числа в нём и в `vehicle.dart` синхронизируются вручную.
Не стал сейчас чинить (не просили, это отдельная задача — подключить
загрузку конфига), просто отметил, чтобы не забыть при следующей правке
характеристик машины.

## Больше машин — 18.09.2026

## Полиция / погоня — 18.09.2026

Дизайн согласован с пользователем заранее (AskUserQuestion, все пункты —
рекомендованный вариант): спавн ближайшей точкой дороги вне поля зрения,
AI едет по дорожному графу (не напролом), арест = контакт + недолгая
близость, максимум 2 машины одновременно ради FPS.

Новые файлы:
- `lib/police/road_pathfinding.dart` — `vehicleHighwayTypes` (в отличие
  от пешеходного набора: residential/unclassified/service/tertiary/
  secondary/primary/living_street, без footway/path/cycleway/steps),
  `buildVehicleAdjacency` (уважает `oneway`, в отличие от пешеходной
  карты соседей), `nearestVehicleNodeId`, `findShortestPath` — обычная
  Дейкстра O(V²) по расстоянию между узлами (граф ~700 узлов, см. диагностику
  ниже — считается редко, не каждый кадр, так что квадратичность не проблема).
- `lib/police/police_car.dart` — `computePoliceInput()`, чистая функция
  без Flutter: курс + текущая позиция + путевая точка → throttle/steer
  (та же пара входов, что и `VehicleControllerComponent.setInput` ждёт от
  джойстика игрока). Газ снижается в крутых поворотах — на полном газу
  AI на скорости срезал угол и утыкался в здание вместо доворота.
- `lib/police/police_system.dart` — `PoliceSystem`: спавнит/удаляет
  патрульные машины по числу звёзд (`min(stars, 2)`), пересчитывает путь
  раз в 2.5 с (`findShortestPath` от ближайшего к машине узла до
  ближайшего к игроку), ведёт машину по путевым точкам через
  `computePoliceInput`. Контакт (≤4 м) дольше 2 секунд → `update()`
  возвращает true — обработка ареста снаружи, в `Game`. Светобалка на
  крыше (statically red/blue, без анимации мигания — лишняя работа на
  каждый кадр ради эффекта, который на слабом Android не окупится) —
  единственный визуальный маркер "это полиция", тот же силуэт седана.
- `lib/police/arrest_state.dart` — `ArrestState`, тот же паттерн
  расшаренного стейта, что и `WantedState`: `Game` пишет момент ареста,
  HUD показывает баннер "ЗАДЕРЖАН" 3 секунды через свой Ticker (см.
  `lib/ui/hud/arrest_banner.dart`, скопирован паттерн из `wanted_stars.dart`).

Изменения в существующих файлах:
- `lib/vehicles/vehicle.dart`: добавлен `VehicleArchetype.police` (тот же
  силуэт седана, белый кузов). `buildVehicle()` разделён на async-обёртку
  (читает JSON по `vehicleId`) и синхронное ядро `buildVehicleWithSpec()`
  — `PoliceSystem` грузит спеку один раз в `PoliceSystem.create()`
  (async, во время `Game.load()`), а сам спавн внутри `update()`
  (который зовётся каждый кадр из синхронного `Game.tick()`) синхронный.
  Добавлен флаг `attachPlayerInput` (по умолчанию true) —
  **важно**: без него AI-машины получали бы `VehicleInputBridgeComponent`
  и слушали бы тот же джойстик, что и машина игрока (бага замечена и
  исправлена ДО коммита, не в проде) — полицейские машины строятся с

сессии, а баг репортился и позже в игре), поэтому заодно закрыт пункт

## Мелкие баги, найденные при аудите оптимизаций — 19.09.2026

Три точечных фикса, без архитектурных изменений (оптимизации сознательно НЕ
трогали — сначала замер, см. следующий раздел):

1. **Погоня перестраивала маршрут только после того, как израсходует
   старый.** `PoliceSystem.update()`: условие было
   `if (unit.path.isEmpty && unit.repathTimer <= 0)` — с `&&` таймер в 2.5 с
   тикал вхолостую, пока в пути оставалась хоть одна путевая точка, и
   патруль ехал туда, где игрок был в момент ПЕРВОГО расчёта. Перестроение
   случалось, только когда машина доезжала до конца устаревшего маршрута —
   оторваться от такой погони было слишком легко. Стало `||`: путь пуст —
   строим немедленно, иначе раз в `repathIntervalSeconds`. Таймер по-прежнему
   взводится внутри условия (в том числе когда `_repath` не нашёл путь) —
   иначе при недостижимой цели Дейкстра считалась бы каждый кадр.
   **Юнит-тестом не покрыть** — `update()` требует живых `BuiltVehicle`
   (меши, GPU-контекст); проверяется только вживую на устройстве.
2. **Debug-линии пешеходов пересобирали GPU-буфер каждый кадр.**
   Конструктор `LineSegmentsGeometry` заводит device buffer, а
   `updateDebugTargetLines` вызывался из `Game.tick()` покадрово — 60 новых
   буферов в секунду на ровном месте (внесено в этой же серии правок, до
   устройства не доехало). Теперь меш перестраивается только когда реально
   изменился набор рёбер (пешеход дошёл до узла и выбрал новую цель).
3. **Та же debug-линия рисовала не то, что проверяет рейкаст.** Рисовалась
   от текущей позиции пешехода до узла-цели, хотя `_isEdgePassable` кидает
   луч от узла ДО узла. Для диагностики это важно — смысл линии в том, чтобы
   увидеть глазами именно тестируемый отрезок; теперь рисуется ребро графа.

## План оптимизации + пресеты качества — 19.09.2026

### Аудит: что из culling реально работает

Проверено по исходникам движка, не по догадкам:

- **Frustum culling работает** — `Node.frustumCulled` по умолчанию `true`,
  чанки/машины вне кадра не рисуются.
- **Depth prepass с early-Z работает, но "случайно"** — включается по условию
  `wantDepthPrepass`, среди слагаемых которого `ambientOcclusion.enabled`
  (scene.dart). То есть он приехал вместе с AO. **Мина: выключив AO ради
  экономии, теряем early-Z**, и fill-bound сцена может стать МЕДЛЕННЕЕ.
- **Деревья не культятся вообще** — `InstancedMesh.cullInstances` по умолчанию
  `false`, батч отсекается как единое целое, а общий bbox 220 деревьев
  покрывает весь исследованный район. Все 220 рисуются каждый кадр.
- **Тени дефолтные и дорогие** — `DirectionalLight` создавался без параметров
  теней: `shadowCascadeCount = 4` (четыре прохода shadow map),
  `shadowMaxDistance = 150`.
- **far = 1000 м** при загруженной геометрии 600x600 м (радиус 1).
- **Occlusion culling в движке отсутствует** — дом за домом всё равно попадёт
  в draw list, единственная защита от overdraw это early-Z.
- **LOD не используется**, но выигрыш ограничен: shadow и depth проходы всегда
  рисуют максимальную детализацию.

### Принцип, который нельзя нарушать (требование пользователя)

Камера влияет ТОЛЬКО на отрисовку. Существование NPC и частота их симуляции —
по расстоянию, никогда по видимости. Технически это безопасно by design:
компоненты тикают, пока узел смонтирован, независимо от видимости (см.
комментарий в `Node.scenePrePass`). Нюанс: у невидимых узлов НЕ тикает
`_animationPlayer` — когда появятся анимированные NPC, позу придётся
досчитывать при возвращении в кадр. Известное нарушение принципа уже в коде:
`PedestrianSystem._respawnNear` телепортирует пешехода за `despawnRadius`,
затирая маршрут (отдельная задача, не оптимизация).

### Стоимость сильно зависит от места на карте

Все замеры выше сняты на открытом спавне. Когда игрок подошёл вплотную к
дому (x=-27.1 z=-5.4, стена на весь экран): **17 FPS, ui 11.4, raster 27.5**
— raster вырос с 2.9 до 27.5, то есть на порядок, при том же пресете (low,

кадр.

**Вывод для будущих замеров: одной точки мало.** Мерить как минимум в
открытом поле и вплотную к застройке — это разные режимы нагрузки
(в поле узкое место CPU, у стены GPU).

**9 лучей обхода препятствий стоили 14 мс — половину кадра**, при том что
GPU в это время занят на 3-4 мс из 16.6. Дорог не сам луч, а то, что каждый
`raycastNode` обходит ВЕСЬ граф сцены: девять загруженных чанков района это
сотни узлов, и на каждый считается обратная матрица плюс тест
ограничивающего объёма — девять раз за кадр.

**Попытка включать лучи через кадр ОТКАЧЕНА — игрок проходит сквозь стены.**
Цифры были соблазнительные (31 -> 43 FPS), рассуждение — "игрок идёт 4.5 м/с,
за кадр это 7 см, на следующем кадре контроллер вытолкнет". Рассуждение
неверное: встроенный контроллер не ВЫТАЛКИВАЕТ из геометрии, он
ПРЕДОТВРАЩАЕТ вход, смещая движение вдоль препятствия. Пропустив кадр, игрок
оказывается внутри стены, и возврата оттуда не предусмотрено — пользователь
зашёл в дом сразу же после сборки. **Обход препятствий нельзя прореживать по
кадрам в принципе.** Экономить здесь можно только числом лучей и шириной
области поиска (свой контроллер), но не частотой проверок.

Урок ещё раз тот же, что с мержем мешей: цифра улучшилась, игра сломалась.
Проверять руками ВСЁ, что трогает коллизии — автотестом не покрыть (создание
геометрии требует живого GPU-контекста, см. "Важный урок по тестированию").

Дальше, если нужны стабильные 60: свой контроллер персонажа вместо
встроенного — 3-4 луча вместо 9 и поиск по узкому поддереву (только чанки
района) вместо всего графа сцены. Встроенный `ThirdPersonControllerComponent`
поднимается до корня сцены (`_rootNode`) и сузить область не даёт, только
`groundLayerMask`. Для пешеходов свой контроллер уже писали — опыт есть.

## Свой контроллер персонажа + деревья в домах — 14.10.2026

**Контроллер** (`lib/player/character_motion.dart`, `character_collision_field.dart`,
`character_controller_component.dart`) заменил встроенный
`ThirdPersonControllerComponent`. Экономия кадра — не в числе лучей, а в
области обхода: лучи идут только по чанкам, чей bbox пересекает коробку
2 м вокруг игрока (обычно один из девяти), плюс машины рядом. Движение —
чистая математика без движка, проверяется headless-тестами
(`test/player/character_motion_test.dart`, луч подменяется аналитическим).

Первая версия кидала 3 параллельных луча вдоль движения — **у угла дома
игрок заходил в здание наполовину** (найдено вживую на iPhone Air): при
движении почти вдоль стены луч вдоль движения встречает её на d/sin(угла),
то есть когда тело уже внутри. Итог — **кольцо из 8 горизонтальных лучей**
вокруг тела, каждое попадание — плоскость стены с ограничением по
перпендикуляру, плюс выталкивание наружу (не быстрее 1.5 м/с), которого у
встроенного не было. Лучи кольца длиной 1.5 x (радиус + шаг): диагональный
луч до стены длиннее перпендикуляра, с короткими тест поймал проникновение
на 14 см. Радиус тела 0.85 -> 0.5 (капсула 0.4). Стоя на месте кольцо не
кидается. За рулём контроллер выключен (раньше невидимый персонаж уезжал с
последним вводом).

Тест "в угол дома не заходит ни под каким углом подхода" гоняет бег в угол
с шагом 10° и проверяет зазор каждый кадр — это главный регрессионный тест.

**Не замерено:** FPS на RMX5303 в `--profile` с новым контроллером. Было
9 лучей по всему графу = 14 мс; сейчас 8+1 по одному чанку.

**Деревья в домах и на дорогах** (`lib/world/vegetation.dart`): место
проверялось лучом только по своему чанку, а меши раскладываются по ячейкам
по центру bbox'а и залезают в соседние. Теперь: проверка по всем
загруженным чанкам 5 лучами (ствол + края кроны), а при загрузке нового

## Фоновый трафик — 14.10.2026

`lib/traffic/` — машины ездят по дорожному графу вокруг игрока (пресет:
`trafficPopulation`, 4/6/10). **Кинематические**, не через
VehicleControllerComponent: тот кидает 3 луча по всей сцене на кадр на
каждую машину — для фонового потока ровно та цена, от которой уходили.
Сквозь дома не проедут, потому что полосы не задевают дома —
`check_road_graph.mjs` (переименован из check_pedestrian_graph) проверяет
теперь и полосы трафика: 0 из 672. Поэтому `service` (проезды к подъездам)
в маршрутах трафика нет — на них правая полоса задевала дома.

Правостороннее движение (полоса 1.5 м от оси), торможение перед
поворотами, очередь за впереди идущей, пропуск сбоку по приоритету,
торможение перед игроком/его машиной/полицией/пешеходами. Машина игрока
врезается в трафик по-настоящему (её лучи видят кузова), пешком сквозь
них не пройти (CharacterCollisionField).

**Симуляция на настоящем графе района** (`test/traffic/traffic_district_test.dart`,
5 игровых минут, 10-15 машин, три сида) нашла три бага, которых глазами
не увидеть:
1. Разворот в тупике по обычному радиусу выносил машину на 7.5 м с дороги
   -> тесный разворот радиусом в полосу.
2. На полпути разворота ошибка курса падала ниже порога, и машина
   возвращалась к широкому радиусу -> гистерезис.
3. Левый поворот начинался на самом узле, машину выносило во встречную,
   где она вставала лбом в лоб со встречной — пробка на 228 с. -> Поворот
   вписывается в пересечение линий полос и начинается за R*tan(угол/2) до
   него.
Итог: съезд с оси <= 3.25 м (внутренний угол перекрёстка), машины не
ближе 2.5 м, никто не стоит дольше 0.3 с.

Не сделано: светофоры, трафик не сбивает пешеходов (тормозит перед ними),
реакции на аварию (машина игрока врезалась — трафик просто стоит, пока
путь не освободится). Застрявшие дольше 20 с переселяются, если игрок
дальше 60 м.

## Угон машин — 14.10.2026

Кнопка машины (`Game.vehicleInteraction`) теперь: сесть в свою / выйти /
угнать. Угнать можно машину потока ближе 4 м и не быстрее 4 м/с (трафик
сам тормозит, если встать перед ним) — кнопка красная. Угон: машина
уходит из потока (поток пополняется в дальнем кольце), на её месте
собирается управляемая того же силуэта и цвета, водитель выскакивает с
водительской стороны и 8 секунд бежит в панике (x3.5 скорости) прочь от
игрока по пешеходному графу, розыск — минимум 1 звезда.

Своя машина после угона остаётся в мире, в неё можно вернуться; брошенных
не больше трёх. Выход из машины — с водительской стороны (слева по курсу),
а не всегда в +X мира.

Попутный баг, который угон сделал бы видимым: `VehicleInputBridgeComponent`
проверял только режим "за рулём", а не какая машина активна — с двумя
машинами игрока джойстик рулил бы обеими. Теперь
`GameModeState.activeVehicle` (тест `vehicle_input_bridge_test.dart`).

## Трафик по асфальту, а не по тротуарам — 14.10.2026

Жалоба: "линии проезда машин на пешеходных областях, светофоры тоже".
Разбор по материалам чанков (что реально нарисовано под полосами):

- **Отладочный слой графа рисовал ВСЁ одним жёлтым** — и пешеходные
  дорожки по газонам тоже. По плитке (PAVING_STONE) трафик не ездит вообще:
  0 точек из 87 650. Теперь слой раскрашен (жёлтый — трафик, серый —
  дворовые проезды service, голубой — пешеходные) и по умолчанию скрыт,
  кнопка `graph` в debug-панели.
- **Настоящий баг: дворовые дороги узкие.** Асфальт `residential` — до
  ~2.0 м от оси (дорога 4 м), `tertiary`/`unclassified` — до ~3.5 м. С
  единым сдвигом полосы 1.5 м кузов свешивался на тротуар на 0.4 м.
  Теперь `laneOffsetFor`: 1.2 м во дворах (10 см борта на бордюре), 1.75 м
  на крупных. Грунтовки (surface=unpaved, Смоленская) нарисованы EARTH —
  это тоже проезжая часть.
- **Столбы светофоров** стояли на 4 м от оси — у дворовых дорог в 2 м от
  края, на газоне. Теперь в 0.6 м за краем асфальта своей дороги.

Узкие полосы разбудили целый класс конфликтов (встречные в 2.4 м друг от
друга). Районная симуляция переведена с "расстояние между центрами" на
честную метрику — пересечение кузовов-прямоугольников (SAT) — и по ней
закрыто по очереди:
1. встречные считали друг друга помехой и вставали лоб в лоб навечно ->
   встречная — помеха только при реальном пересечении бортов;
2. слияние на перекрёстке: две машины свернули на одно ребро и въехали
   друг в друга -> на перекрёсток (3+ направления) по одной: владеет
   выезжающий (раньше въехавший), из подъезжающих — ближайший; остальные
   ждут в 12 м (9 м мало — выходящая из левого поворота ещё не выровнялась);
3. хороводы правил вежливости -> "нетерпение": стоящая 5 с не на красный
   машина перестаёт уступать (физическую помеху не таранит);
4. встречные лоб в лоб на изгибе -> прижимание вправо до 0.8 м, тормозить
   перед встречной только у кузова, нетерпеливая ползёт и подруливает;
5. кружение вокруг точки прицеливания (радиус 4.5 м на любой скорости) ->
   на малой скорости радиус до 2.2 м.
Проверено на 17 сидах по 15 машин x 5 минут: 0 кадров наложения кузовов,
дольше ~19 с (красный) никто не стоит.

Пайплайн (`check_road_graph.mjs`) теперь проверяет и поверхность под
кузовом: проезжая часть >= 97% (сейчас 98.5%).

## День и ночь — 14.10.2026 (MVP, пункт 12)

`lib/time/day_night.dart` — модель (тесты), `day_night_view.dart` — сцена.
**Своя модель солнца, а не DayNightCycleComponent движка**: у того солнце
вставало на западе (в наших осях x — восток, z — юг) и не знало о времени
года. Здесь — широта Оренбурга, склонение по дню года и солнечный полдень
с поправкой на долготу (город на 55° в.д. живёт по UTC+5, полдень ~13:17).
Тесты сверены с реальностью: 14 октября рассвет ~7:57, закат ~18:35,
полуденная высота 29° (в июне 62°).

Сутки — 24 минуты игры, старт 16:30 (закат виден через пару минут). Часы
в HUD, в debug-панели `time +1h`.

- Небо — прежнее дешёвое градиентное, цвета по времени (день -> закат ->
  ночь). Освещение от неба запекается один раз, дальше меняется только
  `environmentIntensity` — перезапекать каждый кадр на слабом Android дорого.
- Направление солнца меняется **ступеньками по 0.5°** (~раз в 2 игровые
  минуты): движок перестраивает кэш теней неподвижных объектов при каждой
  смене направления, а этот кэш на RMX5303 экономил 46 мс.
- Ночью — луна (слабый холодный свет сверху), ночь в игре светлее
  настоящей, иначе играть нельзя.
- Unlit-земля (подложка, ради 92 мс GPU) освещению не подчиняется — ночью
  оставалась ярко-зелёной под чёрным небом. Её цвет теперь затемняется
  вручную (`SkyLighting.unlitTint`).
- Фары всех машин — один общий материал, ночью ярче (с bloom — ореол).
- **Окна домов светятся ночью**: движок не хранит имена материалов glTF,
  поэтому пайплайн (`mark_night_materials.mjs`) помечает материал
  `Windows` emissive-текстурой с нулевой яркостью, игра находит такие
  материалы в загруженных чанках и ночью поднимает яркость. Честно: окон в
  геометрии osm2world мало — 320 треугольников на район, это витрины
  первых этажей; большинство домов нарисованы гладкой штукатуркой.

Не сделано: фонари на улицах, звёзды, освещённые окна у "глухих" домов
(нужны текстуры фасадов), смена погоды.

## HUD в духе GTA IV, но светлее (15.10.2026)

Пожелание пользователя: в горизонтальном режиме — круглый радар, обод
которого слева бронежилет, справа здоровье; в вертикальном — плоский

здоровье.

  convert_to_glb.sh): вид сверху по той же геометрии чанков

- **Радар** (`lib/ui/hud/radar.dart`, ландшафт, сверху слева): карта

  краю, если далеко), полиция мигает красно-синим, офицеры, добыча;
  стрелка игрока по его курсу; «С» на ободе; при розыске обод мигает.
  Дуги: слева бронежилет (синий), справа здоровье (зелёный → жёлтый →
  красный), заполняются снизу вверх.

  плашка-пилюля со сторонами света (С/СВ/В/...), рисками и метками;
  **рамка плашки — как обод радара**: левая половина — бронежилет,
  правая — здоровье, заполняются от середины низа по краю к середине
  верха. Розыск — мигает центральная риска. (Промежуточный вариант с

  картинка карты и точки меток ложатся одинаково при любом повороте).
  Всё строится от векторов камеры (вперёд (sin, cos), вправо (cos, −sin)),
  а не от «географии»: движок левосторонний.
- **Бронежилет** (`PlayerHealth.armor`): принимает урон первым, не
  регенерирует, теряется при смерти; выпадает с убитых копов (шанс 40%,
